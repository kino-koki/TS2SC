日期：2026-11-26 · 核实范围：本地已拉取的 **167 个** SimplCore / TS2SC 源码与文档文件
**结论：不是完全继承。设计确实存在于源码文档里，但实现模块没推送；当前 MiniCPM5-1B 迁移体走的是相反的有词表路径。**

> 未删除/修改/推送任何仓库条目；token 只在进程内存用过，交付物 0 hits。

### ⚠️ 一个必须分清的口径

论文里的 `flat reference alphabet Σ₀ of size V_K`（`SimplCore_完整稿.md` L50、
`SimplCore_ICML2027_main.tex` L133–137）**不是「无词表」证据**。那是合成任务上的

## 三、当前第 1 款模型为什么不算继承

MiniCPM5-1B 迁移体的真实事实，全部来自落盘 manifest：

```
vocab_size                = 130560    （真实 tokenizer.json，9.9 MB 真文件）
tie_word_embeddings       = False
model.embed_tokens.weight = COPY  [130560, 1536]   ← 逐位保留
lm_head.weight            = COPY  [130560, 1536]   ← 逐位保留
```

`contract.py` 的 **I6 铁律**：tokenizer 文件 REAL、非 LFS 指针、`len(tok)==embed.rows`；
`TS2SC_深度重开发方案.md` L96：「服务端**零自定义 BPE / 零 id 重映射**」。

**这条在修乱码上完全正确**（V7 的 R2 tokenizer best-effort、R3 子集 BPE 错位就是乱码总根），
但它定义的是 **「有词表 Transformer 的严格兼容」**，方向与「兼容无词表设计」相反：

- 无词表弱版本要的是 **codec 可插拔**（char/byte/bpe 都能进），当前是**绑定单一 tokenizer**；
- 无词表强版本要的是 **删掉 embed/lm_head**，当前是**两张表全 COPY 且显式校验行数**。

所以：**第 1 款模型 = SimplCore mixer 特性 + 有词表 Transformer 兼容**，
不是「SimplCore 全特性模型」。这句必须改口。

## 四、TS2SC 应该怎么做（方向草案，不伪造实现）

你说的「**TS2SC 应该去使 Transformer 上的模型去兼容其无词表设计**」是对的，
而且正好是它作为 **桥（bridge）** 的本职。分两级，强度差很大：

### L-A · 双轨编解码契约（迁移能做的，弱版本）

把 `contract.py` 的 I6 从「单轨绑定」改成 **双轨**：

| 轨 | 用途 | 约束 |
|---|---|---|
| `tokenizer` 轨 | 现有 219 张量、防乱码、LM 服务 | 保持现有 I6：`len(tok)==embed.rows`、5/5 往返、UTF-8 流式 |
| `byte` 轨 | 无词表入口 | `ByteLevelCodec` 字节流 → 动态分块 → 映射到 **同一 embed 空间**；`OOV=0` 由字节覆盖保证；不新增词表条目、不改 embedding 行数 |

新增可证伪断言（F28 落地后）：同一段中文/emoji/多字节边界，
两条轨的 `id` 不同但**语义单元序列可互相转换**；byte 轨不触发任何 `OUT_OF_RANGE_ID`；
`β=0` 时两轨都逐位等于 teacher。这一级**不删 embedding**，与「融合不替换」不冲突。

### L-B · GlyphStream 真无词表（v2 新架构，迁移做不了）

删除 `nn.Embedding` / `lm_head` / 分词器、输入输出连续向量、原型库解码、教师蒸馏。
这不是 TS2SC 迁移的活，是 **新模型 + 重训 + 蒸馏**（corpus.txt 自己写的是 4–6 周 P1），
而且**直接撞红线**：teacher 全功能层一层不删是 F13 的前提，删了就没有「零回归」可谈。
要做得另起一条线、重跑 L2/L3 配对。

### 我现在不能做的

`docs/BYTELEVEL.md`、`simplcore/core/model/tokenization.py`、`native_mm.py` 没推，
**真实接口长什么样我不知道**。所以本轮**只核实 + 登记缺口**，不猜 `ByteLevelCodec` 的
方法签名、不写一个假的实现、不把「无词表」包装成已继承。

**你推这三样（或对应实现的任意一份）给我，下一轮就能对齐真实接口，把 F28 从
`NOT_INHERITED` 做成 `RUNNABLE` 的双轨契约。** F29 需要另立方案，不在同一轮。
